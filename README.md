# نظام مركز البيان

المشروع يتكون من خادم ASP.NET Core 9، وموقع HTML/CSS/JavaScript، وتطبيق Flutter عربي.

## التشغيل المحلي

شغّل `run.bat` أو:

```powershell
dotnet run --project QuranCircles.Api/QuranCircles.Api --urls=http://localhost:5070
```

قاعدة SQLite المحلية تُختار حسب `DATA_DIR` والمسارات الموجودة. **لا تشغّل نسخة اختبار على قاعدة العمل**؛ استخدم مجلدًا جديدًا عبر `DATA_DIR`. يبدأ الخادم بترقية البنية، وتحويل أي كلمات مرور نصية قديمة إلى تجزئة، ومسح القيم النصية، دون إعادة ضبط كلمات المرور الموجودة.

في قاعدة جديدة، أنشئ حساب الإدارة الأول بتعيين `BOOTSTRAP_ADMIN_PASSWORD`، وحساب المطور عند الحاجة عبر `BOOTSTRAP_DEVELOPER_PASSWORD`، بكلمات مرور خاصة من 12 حرفًا على الأقل. لا توجد حسابات إدارة تلقائية بكلمات مرور عامة. حسابات الطلاب والمعلمين التي لا تُعطى كلمة مرور عند إنشائها تحتاج تعيين كلمة مرور من شاشة إدارة الحسابات؛ لم يعد هناك افتراضي مشترك.

الجلسات القديمة ستحتاج تسجيل دخول جديد بعد تحديث الأمان. تغيير كلمة المرور، وتعطيل الحساب، وتغيير الدور يلغي صلاحية الجلسة القديمة. لا يعيد تفعيل الحساب صلاحية الرموز التي أُلغيت عند تعطيله.

## إعداد الاستضافة

تُضبط الأسرار على الاستضافة، ولا تُحفظ داخل المستودع:

| المتغير | الاستخدام |
|---|---|
| `MSSQL_CONNECTION_STRING` | اتصال SQL Server الفعلي |
| `DATABASE_URL` | اتصال PostgreSQL عند اختياره |
| `DATA_DIR` | مجلد SQLite دائم وقابل للكتابة |
| `JWT_SECRET_KEY` | سر توقيع خاص لا يقل عن 32 بايت |
| `JWT_KEY_FILE` | مسار بديل لمفتاح توقيع دائم خارج مجلد الويب |
| `Sms__GatewayUrl` | بوابة HTTPS تستقبل JSON بالشكل `{recipients: [...], message: "..."}` |
| `Sms__ApiToken` | رمز البوابة، يُرسل كترويسة Bearer |

عند عدم تعيين سر JWT، ينشئ الخادم مفتاحًا عشوائيًا دائمًا في مجلد بيانات المستخدم المحلي. في وضع Production يستخدم مجلد `App_Data` خارج ملفات الويب للمفتاح المحلي، ويرفض مفاتيح التوقيع المعروفة التي كانت منشورة في المصدر. في الاستضافة والحاويات يُفضَّل `JWT_SECRET_KEY` أو مسار مفتاح على تخزين دائم مشترك بين النسخ. تغيير المفتاح يلغي جميع الرموز القديمة.

يحتاج نشر MonsterASP إلى سر GitHub باسم `MONSTERASP_PASSWORD`. أُزيلت كلمة مرور النشر من ملف workflow، وأُزيلت بيانات اتصال قاعدة البيانات من إعدادات المصدر. **دوّر بيانات الاعتماد التي سبق وجودها في Git**؛ حذفها من النسخة الحالية لا يمحو التاريخ أو النسخ المنشورة سابقًا.

خدمة SMS تعيد خطأ واضحًا عند عدم الإعداد؛ لا تعلن إرسالًا وهميًا. نجاح طلب البوابة يعني قبول الطلب، وليس تأكيد وصول الرسالة. تأكيد وصول الرسائل وربط بوابة لها تنسيق مختلف يحتاج إعداد الخدمة المناسبة. إشعار WhatsApp المولد مسودة، وليس إرسالًا تلقائيًا. اعتماد النتائج يتطلب كلمة مرور الحساب الحالية؛ لا توجد رموز تحقق تجريبية ثابتة.

الموقع لا ينقل بيانات الدخول تلقائيًا إلى خادم مختلف عند فشل الاتصال. تطبيق الهاتف يقبل HTTPS للخوادم البعيدة، ويسمح HTTP فقط لـlocalhost وعناوين المحاكي المحلية.

## النسخ الاحتياطي والاستعادة

باستخدام Python 3، اختر ملف قاعدة البيانات **الفعلي** الذي يظهر مساره في سجل بدء الخادم:

```powershell
python tools/sqlite_backup.py --database "مسار قاعدة البيانات/quran.db" --backup-dir "مسار النسخ"
```

أداة SQLite تستخدم واجهة النسخ الاحتياطي، فتشمل البيانات المعتمدة في WAL، وتفحص سلامة النسخة. احفظ نسخة إضافية في مكان منفصل محمي؛ ملفات النسخ تحتوي بيانات المركز.

للاستعادة: أوقف الخادم وكل اتصالات SQLite أولًا، ثم:

```powershell
python tools/sqlite_backup.py --database "مسار قاعدة البيانات/quran.db" --backup-dir "مسار النسخ" --restore-from "مسار نسخة سابقة.db"
```

تتحقق الأداة من المصدر، وتحفظ نسخة من الحالة الحالية قبل الاستبدال، وترفض الاستعادة إذا وُجدت ملفات WAL/SHM/Journal. لا تحذف تلك الملفات يدويًا؛ أغلق الاتصالات واعمل checkpoint صحيحًا. SQL Server وPostgreSQL يحتاجان أدوات النسخ والاستعادة الخاصة بهما؛ هذه الأداة مخصصة لـSQLite.

## المزامنة المحلية

تُحفظ بيانات القراءة والعمليات المؤجلة لكل حساب وخادم على حدة. تُحفظ الجلسة في التخزين الآمن للمنصة. يحتفظ النظام بالعمليات الفاشلة وغير المعروفة بدل حذفها، ويحافظ على العمليات المضافة أثناء المزامنة. مفاتيح العمليات ثابتة عند إعادة المحاولة، ويحفظ الخادم إيصال العملية مع التعديل في معاملة واحدة لمنع تكرار الحضور والتسميع والإعلانات.

لا تُنسب الطوابير القديمة غير المرتبطة بحساب تلقائيًا إلى مستخدم جديد. تبقى البيانات القديمة في تخزين التطبيق للمراجعة اليدوية قبل ترحيلها؛ لا تعِد إرسالها دون معرفة صاحبها.

## التحقق

```powershell
dotnet test QuranCircles.Api.Tests/QuranCircles.Api.Tests.csproj
node --check QuranCircles.Web/app.js
python -m unittest discover -s tools -p "test_*.py"
```

داخل `QuranCircles.Mobile`:

```powershell
flutter pub get
flutter analyze
flutter test
flutter build web --base-href=/mobile/
```

في Windows، إذا فشلت native assets بسبب المسافة في مسار Flutter المحلي، استخدم اسم المسار القصير 8.3 للأداة. إعداد النظام الحالي قد يحتاج دعم symlinks لبناء بعض منصات الحاسوب؛ لا تتطلب اختبارات Flutter تغيير إعدادات النظام عند استخدام SDK عبر مساره القصير و`--no-pub` بعد تثبيت الحزم.

تتحقق اختبارات الواجهات من الدخول والماليات بعروض 320 و360 و768 و1440، وبمقياس خط 100% و150%. هذه ليست ضمانًا لكل نافذة وبيانات على جميع الأجهزة؛ يُعاد فحص الجداول الممتلئة والنوافذ والكيبورد عند تعديلها. GitHub Actions يفحص المصدر والاختبارات قبل النشر والبناء.

## تحديث نسخة MonsterASP الموجودة

ملف المشروع يستبعد `appsettings*.json` من ناتج `dotnet publish`، بما يشمل زر **Git deploy → Build & publish** في MonsterASP. يُحفظ اتصال SQL Server داخل `wwwroot/appsettings.json` على الاستضافة مرة واحدة؛ تحديث البرنامج لا يرسل نسخة الإعدادات الفارغة الموجودة في GitHub فوقه. لا تحذف مجلد الموقع أو ملفات إعداداته عند النشر، واحتفظ بنسخة خاصة من ملف الاتصال خارج المستودع. عند أول نشر إلى استضافة جديدة يجب إنشاء إعدادات الاستضافة أو ضبط متغيرات البيئة قبل تشغيل البرنامج.

ملف Web Deploy يحافظ أيضًا على إعدادات الاستضافة وقاعدة SQLite وملفاتها ومجلد `App_Data`. بيانات SQL Server تبقى في قاعدة الاستضافة وتُحدَّث ملفات البرنامج والواجهة فقط. لا تنسخ قواعد SQLite القديمة إلى SQL Server لاستعادة بيانات موجودة أصلًا فيه.

في **MonsterASP → Git deploy → Protected files** أضف المسارات التالية، كل مسار في سطر مستقل، ثم احفظها قبل النشر. هذه حماية إضافية للإعدادات الموجودة على الموقع حتى عند النشر من نسخة أقدم من المستودع:

```text
appsettings.json
appsettings.Production.json
quran.db
App_Data/
```

تعليمات الاستضافة: https://help.monsterasp.net/websites/git-deploy/github-repository#protected-files

قبل دفع التحديث إلى `main`، غيّر كلمة مرور نشر MonsterASP التي كانت ظاهرة في المستودع العام، وضع الجديدة في GitHub Actions Secret باسم `MONSTERASP_PASSWORD`. ويجب تدوير بيانات دخول قاعدة البيانات التي سبق نشرها مع تحديثها على الاستضافة. ربط GitHub بالشات يتيح الوصول إلى المستودع، لكنه لا يهيئ أسرار GitHub Actions تلقائيًا. لا ترسل الأسرار في المحادثة أو تضعها في commit.
